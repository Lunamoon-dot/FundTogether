# HED-MVP-1 implementation status

This is an implementation evidence note, not a production-readiness claim.
It is separate from the historical Workflow B report.

## Verified local code evidence

- HED escrow contract: full funding, request reserve, vendor acknowledgement,
  deposit/final mechanics, challenge cases, refund base/supplement and scoped
  primary/backup takeovers are implemented in `contracts/src/FundTogetherDisbursement.sol`.
- HED ABI is generated by `backend/scripts/hed/generate-artifacts.cjs`; do not
  copy a contract ABI into a client by hand.
- HED metadata APIs use additive tables/migrations `0018` through `0021`.
  They do not change Workflow A/B projections or migrations.
- Private request evidence is checked server-side for MIME, bytes and SHA-256,
  then linked to the request before it may be frozen. Upload success does not
  mean a payment was approved or sent.
- The frontend HED mode uses chain `31339`, RPC port `9548`, and a distinct
  deployment manifest. It labels draft/frozen records separately from chain
  reserve, vendor acknowledgement, receipt, and indexed state.

## Repeatable checks

Run from the repository root:

```powershell
wsl.exe -d Ubuntu-24.04 --exec sh -lc 'cd /mnt/c/Users/dell/Desktop/FundTogether/contracts && /home/dell/.foundry/bin/forge test --match-path test/unit/Disbursement/FundingAndReservation.t.sol'
cd backend; npm.cmd run build; npm.cmd run artifacts:hed
cd backend; npm.cmd run smoke:hed
cd ..\frontend; npm.cmd run build
```

The HED local chain is intentionally separate. Do not start Anvil manually on
the HED RPC port and do not use an A/B deployment manifest as an HED manifest.
`smoke:hed` creates a new local-only campaign on every run and checks receipt
success, the vendor's balance delta and the final activity state. It never
resets existing local HED state.

## Not yet proven

- A complete live local trace from campaign creation through purchase,
  transport, outcome, indexer projection and refunds.
- Delivery/outcome private/public packages, case material APIs and all resolver
  decision paths.
- All backup-resolver settlement/verification transitions; a blocked liability
  must remain explicit rather than being auto-released.
- Manual wallet/vendor/reviewer acceptance and production suitability.

No local or public deployment, real-token transfer, push, or pull request is
created by this runbook.
